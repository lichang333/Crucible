# 多智能体小团队：实施计划

## 项目目标

做一个由三个智能体组成的小团队：一个写代码，一个写并运行测试，一个负责审查。最终用一套评测回答一个问题：多智能体到底比单个智能体好在哪里，值不值得多花的成本。

建议开始时间：12 月 3 日周四中午两点。预计总共花两到三周的业余时间。

## 开始前的准备

- 选一门你最熟的语言，Python 或 TypeScript 都可以，后面所有代码都用它。
- 准备好一个模型的 API 密钥，先用一个就够了，不要一开始就混用多个模型。
- 建一个空的代码仓库，从第一天起就用 Git 提交，方便回头看每一步改了什么。
- 准备一个日志文件，把每次智能体的输入、输出、耗时、花费都记下来。后面做评测全靠它。

## 第 1 步：定一个很小的任务（约半天）

**目标：** 选一类范围很小、结果容易判断对错的任务，作为整个项目的考题。

**怎么做：**

1. 任务形式统一为：给一段中文需求，产出一个能运行的命令行小工具。
2. 先写出十个这样的需求，难度从简单到中等。例如：统计文本文件的词频；把 CSV 转成 JSON；批量重命名文件；按日期归档文件夹；简单的待办事项命令行。
3. 每个需求配几条人工写的验收标准，比如输入什么、应该输出什么。这些标准以后就是评测的标准答案。
4. 先留出其中三个当调试用，另外七个等到最后评测时才用，避免自己调到过拟合。

**完成标志：** 你手上有十份需求加验收标准，而且你自己手写一遍能确认它们是可实现的。

## 第 2 步：先做写代码智能体（约两到三天）

**目标：** 只用一个智能体，把需求变成代码文件，先跑通最简单的闭环。

**怎么做：**

1. 写一个函数，输入是需求文本，输出是代码文件内容，并保存到磁盘。
2. 提示词里明确写清楚：语言、文件结构、不要多余解释、只输出代码。
3. 给它一个写文件的工具，而不是让它在文本里贴代码再由你去解析，这样更稳。
4. 用三个调试需求各跑几次，观察它哪里会出错，把常见问题记下来。
5. 这个单智能体版本要单独保留，它就是最后评测里的对照组。

**完成标志：** 给一个需求，一条命令就能生成可以运行的代码，至少调试用的三个需求里有两个能跑起来。

## 第 3 步：加测试智能体（约三天）

**目标：** 让第二个智能体根据需求写测试，并真的运行，把失败信息送回给写代码的智能体，形成第一个兜底回路。

**怎么做：**

1. 测试智能体只能看需求，不能看写代码智能体的实现，这样它写的测试才是独立的。
2. 给它两个工具：写测试文件，和运行测试并返回结果。
3. 测试失败时，把错误信息原样交给写代码智能体，让它修改后重试。
4. 一定要设最大重试次数，建议先定三轮，到了就停并标记为失败，不要让它无限循环。
5. 记录每个任务用了几轮、最后过没过，这是评测的核心数据。

**完成标志：** 能看到一个完整过程：代码写错、测试发现、自动修复、最终通过，而且日志里每一轮都有记录。

## 第 4 步：加审查智能体（约三天）

**目标：** 加入第三个智能体，专门挑毛病，让代码在通过测试之外再多一道质量关。

**怎么做：**

1. 审查智能体同时看需求、代码和测试结果，只负责指出问题，不直接改代码。
2. 让它按固定清单检查：有没有漏洞、有没有没处理的边界情况、命名和结构是否清楚、测试是否覆盖了需求里的每一条。
3. 它的输出要结构化，每个问题带上严重程度，只有严重问题才会打回给写代码智能体。
4. 给整个流程设总轮数上限，建议写代码、测试、审查加起来最多五轮，超过就停，标记为失败。
5. 注意观察它是不是在鸡蛋里挑骨头，如果每次都打回，就要在提示词里收紧标准。

**完成标志：** 三个智能体能自动跑完一个任务，日志里能看到每个角色说了什么，而且不会无限循环。

## 第 5 步：写评测并和单智能体对比（约三到四天）

**目标：** 用数据回答多智能体值不值得。

**怎么做：**

1. 用第一步里留着的七个任务，加上调试用的三个，一共十个，分别跑单智能体版本和多智能体版本。
2. 每个任务每个版本至少跑三次，因为模型输出有随机性，只跑一次不可信。
3. 记录四个指标：一次通过率、最终通过率、平均修改轮数、总花费，包括耗时和调用费用。
4. 把失败的案例逐个看一遍，归类：是需求理解错了、测试写错了，还是审查太苛刻。
5. 写一页结论：多智能体在哪类任务上更好，提升了多少，多花了多少钱，值不值得。

**完成标志：** 你手上有一张对比数据表和一页结论，能明确说出多智能体的优势和代价。

## 补充实验：混合模型省成本

**目标：** 验证写代码用强模型、其他角色用便宜模型，能不能在通过率基本不变的前提下，明显降低花费。

**怎么做：**

1. 准备三种配置：全部用强模型；写代码用强模型，测试和审查用中等模型；写代码用强模型，测试用中等模型，审查用便宜模型。
2. 让便宜模型先把长日志和报错压缩成简短摘要，再交给强模型，减少强模型读取的内容。
3. 三种配置都跑同样的十个任务，每个至少三次，记录一次通过率、最终通过率、平均轮数和总花费。
4. 重点观察审查智能体：模型变弱后，是不是开始漏掉真问题，或者乱打回。
5. 如果通过率只掉一点、花费降了不少，就采用混合配置；如果掉得明显，就把审查角色换回更强的模型。

**完成标志：** 你能给出一张三种配置的对比表，并明确说出哪个角色用便宜模型最划算。

## 第 6 步：加路由智能体，自动选模型和思考强度（约三到四天）

**目标：** 在最前面加一个便宜的分诊智能体，让它先判断任务难度，再决定后面用哪个模型、开多大的思考强度。

**怎么做：**

1. 分诊智能体用最便宜的模型，只做一件事：读任务，输出难度等级（简单、中等、困难）和一句理由。
2. 为每个等级定一套配置。简单：单个便宜模型，不开深度思考。中等：写代码用强模型，测试和审查用中等模型。困难：全程强模型，主智能体开高思考强度。
3. 加升级机制：便宜配置失败两次，就自动换成更强的配置重来，并在日志里记下升级原因。
4. 校准分诊智能体：拿十个你已经知道难度的任务，看它分得准不准，重点看有没有把难题误判成简单题。
5. 对比三种方案：全用强模型、固定混合配置、路由自动选择，看通过率和总花费。

**完成标志：** 路由方案的通过率接近全强模型，花费明显更低，而且你能说清楚分诊在哪类任务上容易判断错。

## 实施方案：订阅 CLI 加 API 的混合搭建

**背景：** 你手上有 Grok 和 Gemini 的订阅，可以通过 CLI（Grok CLI、Antigravity 的 agy）使用；另外有 Minimax、DeepSeek、GLM 的 API 余额。思路是让 CLI 担任需要强能力的整段角色，API 负责便宜的杂活和对照实验。

### 一、统一接口层（第一天）

1. 写一个统一函数，例如 run\_agent(role, prompt, workdir)，里面有两种后端：API 后端和 CLI 后端。
2. API 后端用 OpenAI 兼容接口，换模型只需要改 base\_url 和模型名，Minimax、DeepSeek、GLM 都可以走这一套。
3. CLI 后端用子进程调用，例如 agy -p 加提示词，并指定 --output-format json，方便解析结果。
4. 把「角色对应哪个后端、哪个模型」写进一份配置文件，不要写死在代码里。这样第五、六步换配置做对比实验时，不用改代码。
5. API 密钥放进环境变量，不要写进代码和仓库。

### 二、先验证 CLI 能不能无头运行（半天）

1. 用一个最简单的提示词（例如让它只回复 OK），从脚本里调用 agy -p，确认能拿到输出并正常退出。
2. 已有用户反馈过 agy -p 在输出被重定向时可能卡住，所以一定要加超时，建议同时设一个「多少秒没有输出就杀掉」的空闲超时。
3. 如果确实卡住，先更新 agy，仍然不行再考虑社区的无头桥接工具，或用伪终端方式调用。
4. Grok CLI 我没有核实过它的非交互模式，请先自己确认它能不能「一次提示词、输出结果、退出」。如果不能，就让 Grok 只当聊天里的审方案助手，不放进自动流程。

### 三、工作目录隔离与权限（半天）

1. 每个任务用一个全新的临时目录，里面 git init，CLI 的工作目录指向它，不要让 CLI 接触你的真实项目。
2. 无头模式没有人点确认，所以要提前设置好权限模式。只在临时目录里放开权限，其他地方保持默认。
3. 临时目录里不要放密钥和个人文件。
4. 每个任务跑完后保存目录快照，便于评测失败时回头检查。

### 四、日志与成本记录（一天）

1. 每次调用记录：任务编号、角色、后端、模型、输入输出 token、耗时、退出码、重试次数。
2. API 的 token 数取自接口返回的用量字段。agy 可以用 stream-json 输出观察工具调用和 token 用量。
3. 订阅是包月的，没法换算成每次多少美元。评测里对订阅调用用 token 数、耗时和消耗的额度来比较，对 API 调用才折算金额，两类成本分开列，不要硬加在一起。
4. 遇到额度用完或限流，要捕获并等待重试，同时把「被限流」也记进日志。

### 五、推荐的起步配置（起点假设，要用评测验证）

1. 写代码：先用 agy 里最强的模型。要是它不稳定或额度紧张，就退回 DeepSeek 或 GLM 里编码更强的那个。
2. 测试：用 DeepSeek 或 GLM 的 API，成本低、调用频繁。
3. 审查：尽量用和写代码不同厂商的模型，例如写代码用 Gemini，审查用 Grok 或 DeepSeek。不同模型家族的盲点不完全一样，互相挑错的效果通常更好。
4. 摘要日志、任务分诊：用 Minimax 或 GLM 里最便宜的。
5. CLI 调用要串行，不要并发，避免触发限流。

### 六、对照实验设计

1. 配置 A：全部用 API 模型。
2. 配置 B：写代码用 agy，其他用 API。
3. 配置 C：写代码用 agy，审查用 Grok CLI，测试和摘要用 API。
4. 三种配置跑同样的十个任务，每个至少三次，比较一次通过率、最终通过率、平均轮数、耗时、token 用量。
5. 看完数据再决定第六步的路由规则：哪一类任务值得动用订阅里的强模型。

### 七、风险与注意事项

1. 订阅能不能用于自动化批量调用，各家条款不同，开跑之前建议先读一下，避免账号被限制。
2. CLI 版本更新很快，无头模式的行为可能变化，记录你实际使用的版本号。
3. CLI 自带智能体循环，行为比 API 更难预测，评测结果可能波动更大，所以每个任务要多跑几次。
4. 不要把模型输出的命令在真实环境里直接执行，只在临时目录里执行。

### 八、建议的实施顺序

1. 第一天：统一接口层加配置文件，先接通一个 API 模型。
2. 第二天：验证 agy 无头运行，接入 CLI 后端。
3. 第三天：隔离目录、权限设置、日志。
4. 之后：回到前面的第一到第五步，按配置 A、B、C 跑对照实验。

## 收尾与下一步

- 把代码、日志、评测数据和结论整理进同一个仓库，写一份简短的说明文档。
- 复盘时重点想三件事：哪一步最容易出错、兜底回路是否真的有用、评测本身有哪些不足。
- 做完后可以接着做待办里的另外三个项目，也可以给这个项目换更难的任务或换不同的模型，再测一遍。
